# RFP Pursuit Guide

Reference document for the `rfp-context.mdc` Cursor rule and the three RFP skills (`rfp-qualifier`, `rfp-discovery-to-design`, `rfp-assembler`). Contains the Architecture Intent format, C4 conventions, standard pursuit folder structure, and the RFP → ADM phase mapping in full.

---

## Pursuit folder structure

Every pursuit lives under `pursuits/`. The folder structure mirrors the phase sequence.

```
pursuits/
  <client>-<engagement-slug>/
    Phase0/
      bid-no-bid-decision.md
      rfp-requirements-matrix.md
      open-questions-log.md
    Phase1/
      client-context-brief.md
      nfr-catalogue.md
      solution-hypothesis.md
      clarification-qa-log.md          ← living document; update as client responds
    Phase2/
      architecture-intent.md           ← GATE ARTIFACT — must be agreed before Phase 2 proceeds
      capability-map.md
      options-analysis.md
      ADR-NNNN-<slug>.md               ← one file per key decision; use global ADR counter
      sad.md
      nfr-response-matrix.md
      fit-gap-assessment.md
    Phase3/
      phased-roadmap.md
      risk-register.md
      assumptions-exclusions.md
      dependency-log.md
      effort-estimation-workbook.md    ← not generated by skills; author manually
      team-raci.md                     ← not generated by skills; author manually
    Phase4/
      compliance-matrix.md
      executive-summary.md
      commercial-proposal.md           ← not generated by skills; commercial lead authors
      reference-case-studies/
    Phase5/
      presentation-deck.pptx           ← use presentation-skills skill
      clarification-responses.md
```

**Naming convention:** `<client>-<engagement-slug>` should be short, lowercase, hyphen-separated. Prefer two-to-three word slugs. Example: `acmecorp-hrplatform`, `municipality-data-modernisation`.

**Global ADR counter:** ADRs created during a pursuit use the global ADR numbering sequence from `AGENTS.md`. Check the current highest ADR number across the entire repo before creating a pursuit ADR.

## RFP → TOGAF ADM phase mapping

Presales phases are not the ADM, but they draw from it. The mapping below prevents the most common failure: treating architecture as a Phase 2 activity rather than a continuous thread from qualification.

| RFP Phase | TOGAF ADM equivalent | Governing principle |
|-----------|---------------------|---------------------|
| Phase 0 — Qualify | Pre-ADM (commercial gate) | No architecture work before go/no-go is confirmed |
| Phase 1 — Discovery | Phase A — Architecture Vision | Problem before solution; NFRs before design |
| Phase 2 — Solution Design | Phases B / C / D | Capability before technology; ABB before SBB |
| Phase 3 — Delivery Model | Phases E / F (abbreviated) | Roadmap derives from gap analysis, not from project management instinct |
| Phase 4 — Commercial | Outside ADM | Architecture drives commercial; commercial does not redefine architecture |
| Phase 5 — Presentation | Outside ADM | Every assertion in the orals must trace to an artifact |

The most important transition is **Phase 1 → Phase 2**. The Architecture Intent document is the gate artifact. Nothing in Phase 2 starts until it is agreed.

## The Architecture Intent document

The Architecture Intent is a one-to-two page governing narrative produced at the Phase 1/Phase 2 boundary. It is not a full SAD. Its purpose is to establish a single shared understanding of the proposed approach before multiple workstreams begin producing artifacts in parallel.

### Why it matters

Without the Architecture Intent:
- The Executive Summary says "cloud-native microservices"
- The SAD shows a lift-and-shift deployment model
- The effort estimate is sized for Option B when the narrative describes Option A
- The Compliance Matrix references sections of the proposal that do not address the relevant requirements

Each of these inconsistencies is visible to the client's evaluation team. Experienced evaluators read the Executive Summary and then probe the SAD for alignment. Inconsistency erodes confidence more than a known gap with a mitigation plan.

### Format

```markdown
# Architecture Intent — <Client> <Engagement>

> **ADM phase:** A (Architecture Vision)
> **Version:** 0.1 (draft for pursuit lead review) / 1.0 (agreed)
> **Last updated:** <date>

## Problem statement

<One paragraph. What is the client trying to solve? State the business problem, not the technical symptom. Connect to the client's strategic drivers from the Client Context Brief.>

## Proposed capability approach

<What capabilities will the proposed solution deliver? State at ABB level — no product names here. Product names go in the SAD Technology section.>

Example:
> The solution will deliver the following capabilities: API Management (expose and govern all integration touchpoints), Identity & Access Management (unified AuthN/Z for all actors), Event Streaming (decoupled integration between Order Management and Fulfilment), and an Operational Data Store (near-real-time reporting without impacting transactional systems).

## Key architectural decisions already made

<Decisions that constrain the solution design. Brief rationale for each. Full ADRs will be written in Phase 2 for each of these.>

| Decision | Rationale |
|----------|-----------|
| Cloud provider: <Azure / AWS / GCP> | <Why — regulatory, client standard, SA team expertise, etc.> |
| Integration pattern: <Event-driven / Synchronous API / Hybrid> | <Why — NFR-driven, existing estate compatibility, etc.> |
| Build vs. SaaS for <capability>: <approach> | <Why> |

## Assumed principles

<Which principles govern this solution? Cite by P-NN from principles.md, or state the client's equivalent if known.>

- P-03 (ABB before SBB) — no technology selected before capability requirements are confirmed
- P-04 (One SoR per entity) — <entity> will have a single system of record; all other systems consume via integration
- P-05 (Security by design) — threat model is produced in Phase 2, not appended at the end
- <Client principle if known>

## Integration stance

<How does the proposed solution connect to the existing estate? State the approach — not the design detail.>

Example:
> The solution integrates with the existing ERP via published APIs (inbound) and a message broker (outbound). No direct database integration. The existing ESB is treated as a legacy integration layer to be superseded by the new API Management platform within 18 months.

## Explicit out-of-scope

<What is this solution NOT addressing? State it plainly. Every item here becomes an Exclusion entry in the Assumptions & Exclusions document.>

- Replacement of <Legacy System Z> — future phase; referenced in RFP but outside this engagement
- End-user training content — client is responsible for learning design; train-the-trainer is in scope
- Managed service post go-live — separate commercial arrangement

## Open questions that could change this intent

<Link to the Open Questions Log by Q-NNN for any question that, if answered differently, would change a capability, decision, or integration stance above.>

- Q-007: <question> — if the answer is X, the integration stance changes to Y
- Q-012: <question> — if data residency is not EU-only, the hosting model changes
```

### Gate criteria before Phase 2

Before starting Phase 2 artifacts (Capability Map, Options Analysis, SAD), confirm:

- [ ] Architecture Intent reviewed and agreed by pursuit lead
- [ ] Version updated to 1.0
- [ ] High-priority open questions resolved, or documented as assumptions in Phase 1 artifacts
- [ ] EA standards check passed: ABBs named, principles cited, stakeholders and concerns present

## C4 diagram conventions

All architecture diagrams in proposals follow the C4 model. This section defines the expected levels, labelling conventions, and what to include/exclude at each level.

### C4 levels

| Level | Name | What it shows | When to produce |
|-------|------|--------------|-----------------|
| C1 | System Context | The proposed system as a black box, its users, and the external systems it integrates with | Always — this is the minimum viable diagram for any proposal |
| C2 | Container | Major deployable units: applications, services, databases, message brokers, front-ends | Almost always — needed for any non-trivial solution |
| C3 | Component | Internal components of one specific container | Selective — only when an RFP requires it or a key differentiator sits at this level |

C4 Level 4 (Code) is not produced in proposals.

### Labelling conventions

Every element in a C4 diagram must have:
- A **name** (noun, not verb)
- A **technology label** in square brackets: `[React]`, `[Azure Service Bus]`, `[PostgreSQL on Azure]`
- A **description** of what it does (one sentence)

Relationships must have:
- A **label** stating the nature of the relationship and the protocol: `Publishes events [Azure Service Bus / AMQP]`, `Reads/writes [PostgreSQL / JDBC]`

Technology labels in diagrams must match exactly what is named in the SAD Technology Selection section. If the diagram says `[Azure API Management]` but the SAD says "API Gateway", they need to align before submission.

### What every diagram must include

- **Title** — `<System Name> — System Context Diagram` / `Container Diagram` / `Component Diagram`
- **Description** — one paragraph below the diagram: what it shows and what it intentionally omits
- **Legend** — distinguish: systems in scope / external systems / actors / infrastructure
- **Boundary box** — clear visual boundary around what is within scope; everything outside the box is external

### What every diagram must NOT include

- Internal implementation detail at a level higher than the current C4 level
- Technology names without justification in the SAD
- Placeholder boxes labelled "TBD" — if a capability is identified but the technology is not yet selected, label it with the ABB name and mark `[Technology TBC — pending Q-NNN]`

## The one rule

Every artifact in the proposal must be traceable back to a stated client requirement or a documented architectural decision. If it cannot be traced, either it does not belong, or there is a missing decision record.

This applies in the orals more than anywhere else. When the client asks "why did you design it this way?" or "how does this address requirement 4.7?", the answer comes from a specific artifact — not from an individual's memory.
